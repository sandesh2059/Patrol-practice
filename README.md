# Patrol Practice

A small Flutter app built specifically for practicing UI automation testing with
[Patrol](https://patrol.leancode.co/). It's not a real product — it's a
deliberately simple, keyed, testable app used to learn Patrol's syntax:
finding widgets, form validation, navigation, dialogs, and reading widget
state directly from tests.

## What's in the app

- **Login** — email/password validation, password visibility toggle, error
  messages, navigation to sign-up
- **Create account** — full sign-up form, password confirmation, terms
  checkbox, duplicate-email detection, success snackbar
- **Home** — bottom navigation with a counter tab and a task list tab
  (add/delete tasks), plus profile/settings/logout
- **Profile** — view and edit a display name
- **Settings** — switches, radio buttons, a dropdown, and a slider

Accounts are stored locally on-device using `shared_preferences`, so they
persist across app restarts (but **not** across a fresh install — more on
that below).

A default account is auto-seeded on first launch:
```
email:    test@example.com
password: password123
```

## Project structure

```
lib/
  main.dart                    # app entry point, startup gate, routes
  models/
    user.dart                  # AppUser model + UserStore (local persistence)
  widgets/
    primary_button.dart        # reusable button used across forms
  screens/
    login_screen.dart
    create_account_screen.dart
    home_screen.dart
    profile_screen.dart
    settings_screen.dart

patrol_test/
  Login_test.dart               # login validation + auth test cases
  Create_account_test.dart      # sign-up validation + password masking tests
  test_bundle.dart               # auto-generated by Patrol — do not edit by hand

test/
  widget_test.dart               # basic Flutter widget smoke test
```

Every interactive widget in `lib/` has a `Key` (e.g. `Key('emailField')`,
`Key('loginButton')`) so Patrol tests can reliably find them with `$(#keyName)`.

## Requirements

- [Flutter SDK](https://docs.flutter.dev/get-started/install) (this project
  targets Dart SDK `^3.13.0` — run `flutter --version` to check yours)
- [Android Studio](https://developer.android.com/studio) with at least one
  Android Virtual Device (AVD) set up, **or** a physical Android/iOS device
  with developer mode enabled
- [Patrol CLI](https://patrol.leancode.co/getting-started) for running the
  test suite

## Setup

1. **Clone the repo and install Flutter dependencies:**
   ```bash
   git clone <your-repo-url>
   cd patrol_example
   flutter pub get
   ```

2. **Install the Patrol CLI** (only needed once per machine):
   ```bash
   dart pub global activate patrol_cli
   ```
   Make sure `~/.pub-cache/bin` is on your `PATH` — add this to your
   `~/.bashrc` or `~/.zshrc` if `patrol` isn't found after installing:
   ```bash
   export PATH="$PATH":"$HOME/.pub-cache/bin"
   ```

3. **Verify your setup is correct:**
   ```bash
   patrol doctor
   ```
   This checks that Flutter, Patrol, and your platform tooling are all
   correctly wired up before you try running anything.

## Running the app manually

An emulator or physical device must already be running before you do
anything below. Neither `flutter run` nor `patrol test` will start one
for you.

Check a device is available:
```bash
flutter devices
```

If nothing shows up, start your AVD from Android Studio's Device Manager, or
via command line:
```bash
flutter emulators --launch <your_avd_name>
```

Once a device is visible, launch the app:
```bash
flutter run
```

## Running the tests

With a device/emulator already running:

```bash
# Run a single test file
patrol test -t patrol_test/login_test.dart
patrol test -t patrol_test/create_account_test.dart

# Run every test in patrol_test/
patrol test
```

### Important: `patrol test` reinstalls the app every run

Each `patrol test` run performs a fresh install of the app onto your
device/emulator — similar to uninstalling and reinstalling it. This wipes
any locally saved `shared_preferences` data, including previously created
accounts.

This is why the login tests use the seeded default account
(`test@example.com` / `password123`) rather than an account created in a
separate test file — there's no guarantee tests in different files run in
the same "installed session," and relying on that would make tests flaky.

If a specific test needs a custom account (not the seeded one), it creates
that account within the same test, right before logging in with it —
see `Create_account_test.dart` for the pattern.

### `test_bundle.dart`

This file inside `patrol_test/` is auto-generated by Patrol to bundle all
test files into a single entry point that Android/iOS can launch as an app.
You never need to write or edit it by hand — it regenerates automatically
whenever you run `patrol test`.

## Running the plain widget test

`test/widget_test.dart` is a standard Flutter widget test (not a Patrol
test) and doesn't need a device/emulator — it runs in a headless Dart VM:

```bash
flutter test
```

## Known gaps / things to be aware of

- The create-account screen's password and confirm-password fields are
  always masked with no visibility toggle (unlike the login screen, which
  has one). This is intentional in the current version, not a bug.
- `UserStore` is a simple in-memory + local-storage store, not a real
  backend. It exists purely to give the app something stateful to test
  against — see `lib/models/user.dart` for the full implementation,
  including a `clearAll()` helper useful if you ever add tests that need to
  explicitly reset state within a single `patrol test` run (e.g. testing the
  same duplicate-email flow twice back-to-back).
